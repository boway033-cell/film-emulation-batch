# 源归一化：调色之前先判断色彩格式

> 一句话：**RAW 要显影，灰片要反 log，普通成片（含手机照片）原样通过。**
> 本文是 `scripts/source_normalize.py` 的设计说明与实测记录。所有阈值都由实测数据标定，
> 不是拍脑袋设的；所有曲线都写明出处并与独立实现核对过。

---

## 1. 为什么必须做这一步

胶片模拟预设的曲线、色偏、颗粒全部按「**已经正常显影的 sRGB 成片**」标定。
下面三类素材直接喂进去，预设的前提就不成立：

| 输入 | 数据实质 | 直接套预设的后果 |
|---|---|---|
| **RAW**（ARW / CR2 / CR3 / NEF / DNG / RAF / ORF / RW2 / PEF / SRW / X3F…） | 传感器场景线性数据，无白平衡、无色调曲线、无饱和度 | 画面严重偏暗偏灰；白平衡靠猜 |
| **灰片 / Log**（S-Log3 / S-Log2 / V-Log / LogC3 / LogC4 / Apple Log…） | 暗部抬到固定基灰、高光对数压缩、饱和度整体摊薄 | 在错误基准上**再加一次对比、再加一次饱和**，画面发灰发脏 |
| 普通成片 / 手机照片 | 完整显影的成品 | 无需处理，原样通过即可 |

**一个常见误解必须先说清：RAW 不需要反 log。**
Sony 官方技术文档写得很直接：

> RAW is sensor native data and RAW does not apply any color space nor log curve.
> RAW is always recorded by 16bit Scene linear.

机内 Picture Profile 选 S-Log3 只影响**成片**，不影响 RAW 里存的东西。
所以「RAW + 反 log」等于对同一份数据连续两次错误处理。
本工具里 RAW 只走显影分支，灰片只走反 log 分支，两条路互斥。

## 2. 判定流程

```
输入文件
  │
  ├─ 扩展名属 RAW？ ──是──► 显影为中性 sRGB（相机白平衡 / 不自动提亮 / 不反 log）
  │
  └─ 否 ─► 读像素统计（760px 缩略图）
             │
             ├─ 6 项扁平特征计分 ── 未达门槛 ──► 普通成片，原样通过
             │
             └─ 达门槛 ─► 曲线定位
                            │
                            ├─ ① 基灰否决：残差显著为负的曲线直接剔除
                            ├─ ② 场景合理性仲裁：逐个候选反 log，看解出来的
                            │     场景是否像「曝光正常的场景」
                            ├─ ③ 排序：基灰残差 → 机厂牌先验 → 场景中灰先验
                            │
                            ├─ 基灰指纹**确认** （黑位正好落在某条曲线的基灰上）
                            │     → 反 log 还原，置信 medium/high
                            │
                            └─ 基灰指纹**未确认**（画面没有纯黑）
                                  ├─ 扁平特征 ≥5/6 → 还原，置信 low，并明示是推断
                                  └─ 否则 → 保守跳过，列出最可能的曲线供人工确认
```

### 2.1 六项扁平特征

| 判据 | 阈值 | 为什么成立 |
|---|---|---|
| 黑位抬升 | 0.2% 分位 ≥ 0.055 | Log 把线性 0 抬到基灰；正常成片的黑位一般 <0.05 |
| 动态跨度 | p99.5 − p0.2 ≤ 0.74 | 对数压缩把全范围压进中段；正常成片一般 >0.78 |
| 高光余量 | 1 − p99.5 ≥ 0.045 | Log 不会顶到 255 |
| 无深黑像素 | 亮度 <10% 的占比 <0.6% | 基灰抬升后不存在深黑 |
| 无高亮像素 | 亮度 >95% 的占比 <0.4% | 同上 |
| 饱和度摊薄 | 均饱和 ≤0.22 | 色度被对数编码摊薄 |

每命中一项 +1 分。**相机素材 ≥4 分、手机素材 ≥5 分**判为灰片 ——
手机门槛抬高一分是因为误判代价不对称：把正常手机照片当灰片还原会毁图，
而漏掉一张真灰片只是少还原一步。

### 2.2 基灰指纹：唯一硬证据

每条 log 曲线把「线性 0」映射到一个**固定的基灰码值**。真实灰片画面的最暗处
不可能低于该值 —— 这是一条物理约束，可以用来否决曲线。

| profile | 基灰 `enc(0)` | 18% 中灰 | 90% 白 | 出处 |
|---|---|---|---|---|
| `s_log3` | 0.09286 | 0.41056 | 0.58445 | Sony《Technical Summary for S-Gamut3/S-Log3》 |
| `s_log2` | 0.08825 | 0.38497 | 0.62218 | Sony S-Log2 OETF |
| `v_log` | 0.12500 | 0.42331 | 0.58817 | Panasonic《V-Log/V-Gamut Reference Manual》 |
| `logc3` | 0.09281 | 0.39101 | 0.55943 | ARRI LogC v3（SUP3.x / LSEF / EI800） |
| `logc4` | 0.09286 | 0.27840 | 0.41796 | ARRI《LogC4 Logarithmic Color Space》2025-01 |
| `apple_log` | 0.15048 | 0.48827 | 0.68169 | Apple《Apple Log Profile》白皮书 |

**关键发现：基灰只能定位「族」，不能定位曲线。**
S-Log3 / LogC3 / LogC4 的基灰**完全相同**（都是 95/1023 —— Rec.709 视频范围
黑电平的通用设计点），S-Log2 也只低 0.0046。但它们的中间调差别极大：

| 同一张 S-Log3 画面按别的曲线解码 | 渲染结果平均差 |
|---|---|
| vs S-Log2 | 12.3 / 255 |
| vs V-Log | 6.3 / 255 |
| vs LogC3 | 8.6 / 255 |
| **vs LogC4** | **68.3 / 255** |

所以族内必须再裁决一层。本工具用两类信息：
**① EXIF 机厂牌**（Sony→S-Log，ARRI→LogC，Apple→Apple Log，Panasonic→V-Log）；
**② 场景中灰先验**（假设曝光正常、场景中位反射率接近 10% —— 这正是相机测光所用的同一假设）。

族内差异仍然可见时，置信度只标 `medium`，并把备选曲线与它们的渲染差一并列出。
**不假装确定。**

### 2.3 场景合理性检验（第三条独立约束）

反 log 出来的必须像「一个曝光正常的场景」，否则不予还原：

* 中位反射率落在 **0.035 ~ 0.45**（0.10 的 ±2.2 档）
* p99.5 反射率落在 **0.50 ~ 5.0**（真灰片实测上限 3.47 的 1.44 倍）

阈值由实测标定，见下节。这一条的作用是拦住「看着扁平、其实只是雾天/低调拍摄」
的普通成片 —— 那种画面若按某条 log 曲线反解，会得到中位反射率 0.01 量级、
44% 像素被压死的荒谬场景。

> ⚠️ 实现细节（踩过的坑）：这套统计量**必须用 700px 级的图算**。
> 128px 缩略图的 LANCZOS 平滑会把 p99.5 的高光极值抹平 —— 实测同一张图
> 420px 时 p99.5 = 8.12，128px 掉到 5 以下，本该拦下的画面就通过了检验。

## 3. 实测标定与验收

### 3.1 曲线实现正确性

`python scripts/source_normalize.py --selftest --crosscheck`

* **官方锚点**：9 项，全部通过。例如 S-Log3 官方 10bit 表 `0/18%/90% → 95/420/598`，
  实测差 0.00010 以内；ARRI 官方样例 `log_encoding_ARRILogC3(0.18) = 0.3910068`、
  LogC4 `= 0.2783958`、Apple Log `= 0.4882724`，实测差 0.00000。
* **enc/dec 往返**：6 条曲线在 0→4.0 线性域取 4 万点，最大误差 4.2e-06。
* **与 colour-science 0.4.7 独立实现交叉核对**：6 条曲线最大差 5.8e-08。
  （注意 S-Log2 要与 `log_encoding_SLog` 比对 —— 那是码值约定；
  `log_encoding_SLog2` 是 219/155 归一化约定，数值不同。）

自检合计 **46/46 通过**。

### 3.2 判定规则验收

`python scripts/verify/eval_detection.py <成片目录>`

| 组 | 素材 | 期望 | 结果 |
|---|---|---|---|
| A | 灰片·含纯黑（6 条曲线各一） | 判为 log 且锁进同基灰族 | **6/6**（曲线完全正确 5/6） |
| B | 灰片·无纯黑 | 不能当普通成片 | **6/6**（曲线正确 2/6，均标 low 置信） |
| C | 普通成片（39 张真实相机 JPEG） | 绝不能触发还原 | **11/11 抽样全对，误报 0** |

A 组那条「曲线不完全正确」的是 LogC3 被判成 S-Log3 —— 两者基灰只差 0.00005，
单张 8bit 图在数学上不可能区分，这是已知边界而不是缺陷。

### 3.3 阈值是怎么定下来的

第一版规则在 39 张真实相机 JPEG 上误报 **4 张**（把低对比、暗部的普通照片当成灰片），
一旦误判就会把好照片还原坏 —— 这是最不可接受的错误类型。逐案分析：

| 文件 | 得分 | 解码后中位反射率 | 解码后 p99.5 | 结论 |
|---|---|---|---|---|
| DSC05718 | 4/6 | 0.079 | **19.96** | p99.5 越界 → 拦下 |
| \_DSC5701 | 4/6 | **0.016** | 0.17 | 中位与 p99.5 双双越界 → 拦下 |
| \_DSC5709 | 4/6 | **0.009** | 2.64 | 中位越界 → 拦下 |
| \_DSC5713 | 4/6 | 0.274 | **14.00** | p99.5 越界 → 拦下 |
| 真灰片（9 组） | 4~6/6 | 0.097~0.103 | 0.94~3.47 | 全部在带内 |

于是取带：中位 [0.035, 0.45]、p99.5 [0.5, 5.0]，
**4/4 误判被拦、9/9 真灰片通过**，误报降为 0。

## 4. RAW 显影

固定参数（不给用户「猜参数」的机会）：

| 项 | 取值 | 理由 |
|---|---|---|
| 白平衡 | `use_camera_wb=True` | 恢复拍摄时的色温，而不是软件的平均值 |
| 自动提亮 | **关** | 自动提亮会改写曝光意图 |
| 色彩空间 | sRGB | 与预设标定一致 |
| 内部精度 | 16bit | 曲线运算前不引入 8bit 量化 |
| Gamma | `gamma=(1,1)` | 取得线性 RGB；曝光和色调锚定必须在线性域进行 |
| 去马赛克 | libraw 默认（可 `--raw-denoise light/full` 开 FBDD） | 高 ISO 夜景可用 |

### 4.1 曝光锚定四档

相机 JPEG 包含机内曝光与色调处理，中性线性 RAW 需要选一个曝光锚定方式：

| 模式 | 做法 | 适用 |
|---|---|---|
| **`reference-tone`（默认）** | 先对齐中位亮度，再将参考成片分位曲线作用于**像素亮度**，以同一比例缩放 RGB | 有相机直出可参照；预览需检查高光 |
| `reference` | 以同目录同名成片（相机 JPEG）的**线性中位亮度**为基准，求单一增益 | 只想要中性线性，自己接后续色调 |
| `auto` | 无参考成片时把 p99.5 锚定到 sRGB 0.95（上限 +4 EV） | 只有 RAW，没有同参考成片 |
| `none` | 完全不动曝光 | 自己控制 |

`reference-tone` 更接近相机 JPEG 的亮度分布，适合作为按成片标定的预设输入。
曲线只按亮度计算，RGB 同比缩放，以免在近白区域把微小通道差异放大成青紫色带。
高亮天空和大量近白像素仍可能使分位曲线放大噪声；如果预览出现异常，
改用 `reference`，只对齐亮度而不迁移相机曲线。曝光锚定是场景相关的，不能仅凭默认值省略预览。

没有同参考成片时自动退回 `auto`，并在 `note` 里写明「无同参考成片，退回自动锚定」。

### 4.2 朝向

实测 ILCE-6300 竖拍 RAW 的 `sizes.flip = 6`，而
**rawpy 的 `postprocess()` 已经按相机方向旋转过输出**
（`user_flip` 默认 −1 = 用相机值）：`_DSC5690.ARW` 输出数组 (6024, 4024, 3)
→ PIL 尺寸 (4024, 6024) 竖幅，与相机 JPEG 摆正后的 (4000, 6000) 同向。
**自己再转一次就横过来了。** 但 `sizes.width/height` 报的是**传感器方向**，
所以 `probe()` 里的显示尺寸在 90° 翻转时需要交换宽高。

### 4.3 性能

24MP ARW：显影约 **7.4 秒**（含去马赛克），下游渲染约 11 秒，6 进程并行。
83 张全流程约 4~5 分钟。

## 5. 已知边界（写清楚，不掩盖）

1. **单张 8bit 图无法在数学上区分「log 编码的暗场景」与「正常显影但扁平的照片」。**
   这是问题的本质，不是实现的缺陷。所以判定只承诺两件事：
   可靠的「**扁平与否**」二值判断，以及**有硬证据时才锁定具体曲线**。
2. **画面没有纯黑时曲线是推断。** 中灰先验（场景中位 ≈10%）在雾天、夜景、
   高调棚拍等场合会失准。此时置信度一律标 `low`，并用 `--source log` 可强制。
3. **Log 且高光已触顶的画面会被保守跳过**（p99.5 解码后超过 5.0）。这是刻意的：
   宁可少还原一步，也不把正常照片改坏。
4. **Canon Log 未收录。** 我核对过两处公开实现（v1 与 v1.2 系数不同），
   都不能同时复现 Canon 官方表格在 0%/18%/90%/800%/1600% 五点的数值。
   宁可不做，也不放一条错的曲线进来。需要的话按 `_register(...)` 的模板自行补齐即可。
5. **HEIC / HEIF 不支持**（Pillow 需 `pillow-heif` 插件）。这类文件会被标为
   `unsupported` 并给出提示，不会静默跳过。
6. **不做色彩空间转换**：只处理「编码曲线」，不在 S-Gamut / V-Gamut / BT.2020 等
   广色域与 sRGB 之间做矩阵转换。若素材本身是广色域，色相会有偏差。

## 6. 命令行

```bash
PY="<python>"; S="<repo>/scripts/source_normalize.py"

# 只判断，不写图（先把「色彩格式是什么」看清楚）
"$PY" "$S" ./photos

# 判断 + 还原写出
"$PY" "$S" ./photos -o ./normalized

# 强制：已知是 S-Log3 灰片
"$PY" "$S" ./photos -o ./out --source log --log-profile s_log3

# 强制跳过（确认这批就是正常成片）
"$PY" "$S" ./photos -o ./out --source standard

# RAW：无同参考成片时
"$PY" "$S" ./raw -o ./out --raw-anchor auto --raw-denoise light

# 自检 / 列曲线
"$PY" "$S" --selftest --crosscheck
"$PY" "$S" --list-profiles
```

在引擎里（`film_emulate.py`）这是**默认开启**的 `--source auto`：

```bash
# 直接对 RAW 批量套胶片预设（自动显影 + 反 log）
"$PY" film_emulate.py -i ./raw -p portra400 --jobs 6

# 看判定过程，并把判定与还原参数落盘
"$PY" film_emulate.py -i ./photos -p superia400 --prep-json prep.json
```
